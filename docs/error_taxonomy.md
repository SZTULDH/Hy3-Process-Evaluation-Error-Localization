# 错误类型体系

对应 `app/evaluator/taxonomy.py`。每个类型都标明了它通常**首次暴露**的过程步骤，
用于把错误归类与步骤级定位对齐。

| 代码 | 类型 | 说明 | 典型首发步骤 |
| --- | --- | --- | --- |
| `MISREAD` | 题意误读 | 对输入输出格式、约束条件或语义理解错误 | 解题思路 |
| `ALGO` | 算法选择错误 | 选用的算法或数据结构无法正确/高效地解决问题 | 解题思路 |
| `COMPLEXITY` | 复杂度分析错误 | 声称的时间/空间复杂度与实际实现不符 | 复杂度分析 |
| `EDGE` | 边界处理缺失 | 未处理空输入、单元素、极值、重复元素等特殊情况 | 关键边界与处理策略 |
| `LOGIC` | 实现逻辑缺陷 | 代码存在逻辑漏洞（即使公开测试通过） | 代码实现 |
| `STATE` | 状态管理错误 | 变量更新、累积量维护、状态重置有误 | 代码实现 |
| `TERMINATION` | 终止条件错误 | 循环或递归的终止/边界条件有误，导致死循环或漏解 | 代码实现 |
| `HALLUCINATION` | 幻觉 | 编造不存在的 API、复杂度结论或测试结果 | 自测说明 |
| `INCONSISTENT` | 描述与实现不一致 | 文字思路正确但代码未体现，或反之 | 代码实现 |
| `FALSE_POSITIVE` | 测试覆盖不足导致的伪正确 | 公开测试通过但对抗测试失败 | 代码实现 |

## 类型判定的证据来源

| 类型 | 规则通道能否判定 | 依据 |
| --- | --- | --- |
| `COMPLEXITY` | 部分 | AST 静态分析最大循环嵌套深度，与声称的 `O(...)` 比较 |
| `EDGE` | 能 | 题集声明的 `required_edge_cases` 与边界段落的覆盖比对 |
| `FALSE_POSITIVE` | 能 | 公开测试全过 + 对抗测试失败 |
| `LOGIC` | 能（仅当已暴露） | 公开测试失败或执行异常 |
| `TERMINATION` | 能 | 用例超时 |
| `HALLUCINATION` | 能（仅自测类） | 自测说明声称全过，但对抗测试存在失败 |
| `ALGO` / `MISREAD` | 不能 | 需要语义理解，只有 LLM Critic 通道能覆盖 |
| `STATE` / `INCONSISTENT` | 不能 | 同上 |

这张表解释了为什么**规则通道单独运行时，思路层错误的定位会偏晚**：
它只能观察到"某个用例挂了"这一结果，无法反推"选这个算法本身就是错的"。
接入 Hy3 Critic 后这一层才被覆盖。

## 关于定位粒度

"第一个不成立的步骤"按以下顺序取首个被判 `flawed` 的段落：

```
step_1_approach → step_2_complexity → step_3_edge_cases
                → step_4_implementation → step_5_self_test
```

`解题思路` 与 `复杂度分析`、`边界` 与 `实现` 之间的责任边界存在人为划定的模糊地带
（例如"暴力枚举"到底是思路问题还是复杂度问题），因此验证脚本同时报告
top-1 准确率与 ±1 容差准确率。
